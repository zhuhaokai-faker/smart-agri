# 启动与请求流程

> `python run.py` 之后到底发生了什么？一个 HTTP 请求进来又经过哪些环节？
> 这份文档按**实际代码顺序**逐层拆解，每一步都标注了所在文件和"为什么是这个顺序"。

---

## 一、全局视角

```
┌──────────────────────── 进程启动（只发生一次） ────────────────────────┐
│                                                                        │
│  run.py 模块级代码                                                      │
│    ├─ sys.path.insert(项目根)        让 scripts/ 也能 import 到项目模块   │
│    └─ from env_check import check    环境预检工具类                       │
│                          ↓                                             │
│  main()                                                                │
│    ├─ argparse                       解析 --port / --prod               │
│    ├─ check()                        ★ 预检解释器：不对就退出并给提示     │
│    ├─ from app import create_app     ★ 触发整条 import 链（见第二节）     │
│    ├─ app = create_app()             ★ 组装应用（见第三节）               │
│    └─ app.run(...)                   启动 Werkzeug 开发服务器             │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
                                  ↓ 监听 127.0.0.1:5000
┌──────────────────────── 每个 HTTP 请求（重复发生） ─────────────────────┐
│                                                                        │
│  Werkzeug 收包 → Flask.wsgi_app → 推入请求上下文                        │
│    → URL 路由匹配 → 装饰器链（登录/权限）→ 视图函数                      │
│    → Service 层（业务逻辑 + 原生 SQL）→ SQLAlchemy → PyMySQL → MySQL     │
│    → Jinja2 渲染模板 → 响应返回 → 弹出上下文（归还数据库连接）            │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

## 二、启动阶段（1）：import 链是怎样展开的

从 `run.py` 敲下回车开始，**模块级代码**按下面的顺序执行。
注意 `main()` 里的 `from app import create_app` 这一行才是真正的起点 ——
它触发了一连串的模块加载。

```
run.py  (模块级)
│
├─ import argparse / sys / pathlib
├─ BASE_DIR = Path(__file__).resolve().parent
├─ sys.path.insert(0, BASE_DIR)          ← 让 "from app import ..." 能找到
└─ from env_check import check
      └─ env_check.py 加载（只用了标准库，不依赖任何第三方包）
            ↑ 这一点很关键：预检模块自己不能有第三方依赖，
              否则它自己就会因为环境不对而导入失败，失去意义
```

```
main() 开始
│
├─ argparse 解析参数
├─ check()                               ★ 环境预检
│     ├─ sys.prefix 是不是虚拟环境？
│     ├─ 是不是**本项目**的 .venv？
│     └─ 6 个关键依赖能否 import？
│   任何一项不过 → 打印可操作提示 → sys.exit(1)
│
├─ from app import create_app            ★ 这一行触发下面全部
│  │
│  ├─ app/__init__.py  (模块级)
│  │   ├─ import logging / sys
│  │   ├─ from flask import Flask, jsonify, render_template, request
│  │   ├─ from werkzeug.exceptions import HTTPException
│  │   ├─ from config import Config
│  │   │     └─ config.py 加载：
│  │   │          ├─ load_dotenv(BASE_DIR/'.env')  ← 读 .env 写入 os.environ
│  │   │          ├─ DB_CONFIG = {...}             ← 从 os.environ 取值
│  │   │          ├─ SQLALCHEMY_DATABASE_URI = ...
│  │   │          └─ class Config                  ← 只是定义，还没生效
│  │   └─ from .extensions import db, login_manager
│  │         └─ extensions.py 加载：
│  │              ├─ db = SQLAlchemy()             ← 空壳，还没绑定 app
│  │              ├─ login_manager = LoginManager()
│  │              └─ login_manager.login_view = 'auth.login'  ← 未登录跳哪
│  │
│  └─ （此时 create_app 函数才被定义出来，尚未调用）
│
└─ app = create_app()                    ★ 见下一节
```

> **为什么 `sys.path.insert` 要放在 `from app import ...` 之前？**
> 因为 `run.py` 在项目根目录，直接跑时 `sys.path[0]` 已经是项目根了 ——
> 但 `scripts/` 下的脚本不是。统一显式插入一次，两类入口行为一致。

## 三、启动阶段（2）：`create_app()` 内部

```python
def create_app(config_class=Config):
    app = Flask(__name__)                      # ①
    app.config.from_object(config_class)       # ②

    db.init_app(app)                           # ③
    login_manager.init_app(app)                # ④

    from . import models                       # ⑤ ★ 顺序不能换

    from .blueprints import (admin, analytics, ...)   # ⑥
    app.register_blueprint(auth.bp)            # ⑦ × 9 次
    ...

    _register_jinja(app)                       # ⑧
    _register_errors(app)                      # ⑨
    _register_cli(app)                         # ⑩
    _setup_logging(app)                        # ⑪

    return app
```

### ① `Flask(__name__)`
创建应用对象。此时还没有任何路由、任何配置。

### ② `app.config.from_object(Config)`
把 `config.py` 里 `class Config` 的**大写属性**拷进 `app.config`。
所以 `Config.SECRET_KEY`、`Config.ALLOW_REGISTRATION` 之后都能用
`app.config['SECRET_KEY']` 取到。

### ③④ `db.init_app(app)` / `login_manager.init_app(app)`
**延迟绑定**：扩展对象在 `extensions.py` 里是模块级单例（`db = SQLAlchemy()`），
`init_app` 才把它和具体的 app 实例关联起来。

> 为什么不在 `extensions.py` 里直接 `SQLAlchemy(app)`？
> 那需要先有 app，而 app 又要在工厂里创建 —— 循环依赖。
> 这就是"扩展单例 + 延迟绑定"这个模式存在的理由。

### ⑤ `from . import models` —— **顺序是硬性要求**

这一步会依次加载：

```
app/models/__init__.py
  ├─ core.py       User / Farm / Plot / Crop
  │     └─ @login_manager.user_loader  ★ 见下方说明
  ├─ operation.py  Planting / FarmingLog / InputCost
  └─ result.py     WeatherDaily / YieldRecord / AuditLog
```

**必须先 `init_app` 再 import models。** 因为模型类继承的是 `db.Model`，
如果 `db` 还没绑定到 app，SQLAlchemy 会报 `No application found`。

**`@login_manager.user_loader` 是一个 import 时的副作用。**
它写在 `core.py` 的模块级：

```python
@login_manager.user_loader
def load_user(user_id):
    return db.session.get(User, int(user_id))
```

这行装饰器在模块被导入时就**把函数注册进了 login_manager**。
所以只要 `models` 被 import 过，Flask-Login 就能在每次请求时
用 session 里的 `user_id` 还原出 `User` 对象。

> ⚠️ 如果忘了 import models，或者 `models/__init__.py` 没把 `core` 导出来，
> 这个注册就不会发生，表现为**登录后 `current_user` 永远是匿名的** ——
> 而且不报错。这也是为什么 `models/__init__.py` 要把所有模型都 import 一遍。

### ⑥ `from .blueprints import (...)` —— 9 个蓝图模块被加载

每个蓝图模块在**模块级**做两件事：

```python
bp = Blueprint('auth', __name__)          # 创建蓝图对象

@bp.route('/login', methods=['GET','POST'])
def login(): ...
```

`@bp.route` 只是把"路径 → 视图函数"的映射**记在蓝图对象上**，
此时还没有注册到 app。

### ⑦ `app.register_blueprint(bp)` × 9

**这里才是路由真正生效的地方** —— 蓝图里攒的那些规则被合并进 app 的 URL Map。
注册顺序会影响 URL 匹配的优先级（本项目各蓝图的前缀不重叠，所以无所谓）。

注册的 9 个蓝图：

| 蓝图 | 前缀 | 职责 |
|---|---|---|
| `auth` | （无） | 登录 / 登出 / 改密 / 注册 |
| `admin` | `/admin` | 用户管理（仅管理员） |
| `dashboard` | （无） | 首页看板 |
| `base_data` | （无） | 地块 / 作物 / 农场 |
| `production` | （无） | 批次 / 农事 / 产量 |
| `weather` | `/weather` | 气象数据 |
| `analytics` | `/analytics` | 8 组分析 |
| `map` | `/map` | 地块地图 + 指标 API |
| `audit` | `/audit` | 操作审计 + 字段级变更 |

### ⑧~⑪ 尾部的四件事

| 步骤 | 做了什么 |
|---|---|
| `_register_jinja` | 注册模板过滤器（`num`/`pct`/`signed`…）和全局变量 |
| `_register_errors` | `@app.errorhandler`，JSON 请求返回 JSON、页面请求返回 HTML |
| `_register_cli` | 注册 `flask stats` 命令 |
| `_setup_logging` | 非 debug 模式下加 stdout handler |

### 回到 `run.py`

```python
print(横幅...)                              # 打印解释器和访问地址
app.run(host, port, debug=not args.prod)    # 启动 Werkzeug
```

`app.run()` 是**阻塞**的：绑定端口、进入事件循环，直到 Ctrl+C。

## 四、请求阶段：一个 HTTP 请求的完整旅程

以**已登录的农艺师访问 `/plots/1/edit`** 为例：

```
① 浏览器  GET /plots/1/edit
        ↓ TCP
② Werkzeug 开发服务器
      解析 HTTP → 构造 WSGI environ → 调用 app(environ, start_response)
        ↓
③ Flask.wsgi_app
      ├─ 推入 RequestContext（同时推入 AppContext）
      ├─ 从 Cookie 里取 session（用 SECRET_KEY 验签）
        ↓
④ URL 路由匹配（werkzeug.routing）
      找到 endpoint = 'base_data.plot_edit'，view_args = {'plot_id': 1}
        ↓
⑤ full_dispatch_request → preprocess_request
      执行所有 before_request 钩子（本项目没注册）
        ↓
⑥ 调用视图函数 —— 但实际进入的是**装饰器链**
        ↓
   ┌─────────────────────────────────────────────────────┐
   │  装饰器的执行顺序是**自下而上**包装的                  │
   │                                                      │
   │      @bp.route(...)          ← 最后包装（最外层）      │
   │      @login_required         ← 中间                  │
   │      @editor_required        ← 最先包装              │
   │      def plot_edit(plot_id): ← 函数本体              │
   │                                                      │
   │  装饰时（import 时）：编辑器从下往上套                  │
   │  调用时（请求时）：从外往内 —— 先 login 再 editor      │
   └─────────────────────────────────────────────────────┘
        ↓
   一是 login_required：
      session 里有 _user_id？
        ├─ 没有 → 跳 /login?next=/plots/1/edit（302）
        └─ 有   → 调用 load_user(user_id)
                    ↓
                  db.session.get(User, 1)   ★ 第一次真正碰数据库
                    ↓
                  把 User 对象放进 current_user
        ↓
   二是 editor_required：
      current_user.can_edit ？（role in (1, 2)）
        ├─ 否 → abort(403)
        └─ 是 → 继续
        ↓
⑦ 视图函数本体
      plot = Plot.query.get_or_404(plot_id)     ← ORM 查询
      组装数据 → render_template('plot_edit.html', plot=plot)
        ↓
⑧ Jinja2 渲染
      ├─ 解析 plot_edit.html → 发现 {% extends 'base.html' %}
      ├─ 加载 base.html → 渲染各 block
      ├─ 过滤器处理（{{ plot.area_mu | num(1) }}）
      └─ 拼成 HTML 字符串
        ↓
⑨ Flask 构造 Response（200 + HTML + Content-Type）
        ↓
⑩ 弹出 AppContext → Flask-SQLAlchemy 的 teardown 触发
      db.session.remove()      ★ 关闭会话，连接归还连接池
        ↓
⑪ 返回浏览器
```

### 对比：分析页的链路（`/analytics/gdd`）

```
视图 analytics.gdd()
   ├─ Planting.query...first()             ← ORM
   ├─ A.gdd_curve(pid)                     ← Service 层
   │     └─ q('gdd_curve', """SELECT ...""", {'pid': pid})
   │           ├─ SQL['gdd_curve'] = sql   ← 登记 SQL 原文（给页面展示用）
   │           └─ raw_query(sql, params)
   │                 └─ db.session.execute(text(sql), params)
   │                       └─ SQLAlchemy → PyMySQL → MySQL
   └─ render_template('analytics/gdd.html', curve=..., SQL=A.SQL)
         └─ 模板里 SQL.gdd_curve 拿到的就是**刚才执行的那条语句原文**
```

> 这就是"页面上展示的 SQL 一定等于实际执行的 SQL"的实现原理 ——
> 不是抄了一份，而是**同一个字符串对象**。

## 五、数据库连接的生命周期

```
进程启动
  │
  ├─ db.init_app(app)  创建 Engine，但**不建立任何连接**
  │
  ├─ 第一个请求触发第一次查询
  │     └─ 连接池发现没有可用连接 → 新建一条 TCP 连接（握手的开销在这里）
  │
  ├─ 后续请求复用池里的连接（pool_size=10）
  │
  └─ 每个请求结束时
        db.session.remove() → 会话关闭，连接**归还池中（不是关闭）**

连接池参数（config.py）：
  pool_size     = 10      最多 10 条常驻连接
  pool_recycle  = 3600    连接满 1 小时强制重建
  pool_pre_ping = True    取用前先 ping，失效则自动重建
```

**`pool_recycle` 和 `pool_pre_ping` 为什么必要**：

MySQL 默认 `wait_timeout = 28800`（8 小时）。超时后服务端**单方面关闭**连接，
但客户端池里还留着这条"死连接"。下次拿它发请求就报：

```
(2006, 'MySQL server has gone away')
```

- `pool_recycle=3600` → 主动在 1 小时后就丢弃重建，永远抢在服务端超时之前
- `pool_pre_ping=True` → 拿连接前 ping 一下，兜底防止漏网之鱼

这是"能跑一整天但第二天早上必挂"这类问题的标准解法。

### 关于钩子：本项目自己没注册，但框架注册了两个

```bash
grep -rn "teardown\|before_request\|after_request" app/ --include="*.py"
# → 无结果（项目自己的代码里一个都没有）
```

但这**不代表运行时没有钩子**。实测 `app.after_request_funcs` 会发现框架装了两个：

| 钩子 | 谁注册的 | 作用 |
|---|---|---|
| `after_request` | **Flask-Login** | `login_manager._update_remember_cookie` —— 刷新"记住我"的 Cookie |
| `teardown_appcontext` | **Flask-SQLAlchemy** | `extension._teardown_session` —— **这就是上面 `db.session.remove()` 的来源** |

> 上面流程第 ⑩ 步说的"弹出 AppContext → Flask-SQLAlchemy 的 teardown 触发"，
> 指的就是 `_teardown_session`。**它是框架装的，不是我们写的** ——
> 所以 `grep` 项目源码找不到它，得去 `app.after_request_funcs` 里看才知道。

### 关于事务：本项目没有**自动提交**

框架注册的这两个钩子**都不涉及提交**：
- Flask-Login 那个只管 Cookie
- Flask-SQLAlchemy 那个只 `remove()` 会话（关会话、归还连接），**不会隐式 commit**

所有写操作都是**显式** `db.session.commit()`，没有依赖框架的自动提交。

> Flask-SQLAlchemy 3.x 已移除"请求结束自动提交"的行为。
> 更早的版本有这个魔法，但那是坏设计 —— 视图函数中途 return 或抛异常时
> 到底提没提交，很难推理。显式提交让"事务边界在哪"一目了然。

⚠️ **这带来一个必须注意的约束**：Service 层里 `db.session.add(...)` 之后
**必须**有对应的 `commit()`，否则数据写不进去 —— 而且不报错。

例如 `audit_service.log()` 就是这样设计的：

```python
def log(...):
    db.session.add(entry)
    # 故意不 commit —— 让审计日志和业务变更在同一个事务里提交
    return entry
```

调用方负责 commit，这样"业务成功但审计丢失"或反过来的情况都不会发生。

## 六、几个容易搞错的点（面试常问）

### Q1：装饰器的执行顺序？
**包装时自下而上，调用时从外到内。** 所以：

```python
@bp.route(...)        # 第 3 个包装（最外层）
@login_required       # 第 2 个包装
@editor_required      # 第 1 个包装
def view(): ...
```
运行时先查登录（未登录 → 302 跳登录页），再查权限（权限不够 → 403）。
**顺序反了就会把"没登录"也报成 403**，用户看到的是一个他没权限的页面而不是登录页。

**两个权限装饰器的分工**（按破坏半径，不按功能模块）：
- `editor_required` —— role ∈ {1 管理员, 2 农艺师}。用在**可逆**的写操作上，
  比如编辑地块、编辑产量记录。
- `admin_required` —— role = 1。用在**不可逆**的操作上，
  比如删除产量记录（删完会影响所有分析结果）。

所以同一份资源的"编辑"和"删除"用不同装饰器是完全正常的：

```python
@bp.route('/yields/<int:yid>/edit',   methods=['GET','POST'])
@login_required
@editor_required        # 农艺师也能改

@bp.route('/yields/<int:yid>/delete', methods=['POST'])
@login_required
@admin_required         # 只有管理员能删
```

前端按钮也按同一套规则显隐（`current_user.can_edit` / `current_user.is_admin`），
但**前端隐藏只是"别让你点了才发现不行"** —— 真正拦住越权的是这里的装饰器。

### Q2：为什么 `models` 必须在 `init_app` 之后 import？
模型类继承 `db.Model`。`db` 没绑定 app 时，SQLAlchemy 不知道该用哪个配置，
直接报 `No application found`。这是 Flask-SQLAlchemy 的硬性顺序要求。

### Q3：`current_user` 是怎么来的？
每次请求，Flask-Login 从签过名的 Cookie 里读出 `_user_id`，
调用**在 `core.py` 里用 `@login_manager.user_loader` 注册的** `load_user()`，
查库还原成 `User` 对象。

⚠️ 这意味着**每个请求至少一次数据库查询**（还原当前用户）。
本项目没做缓存，量小无所谓；高并发场景要把它缓存起来。

### Q4：为什么 `extensions.py` 单独一个文件？
因为 `models` 要用 `db`，而 `db` 如果定义在 `app/__init__.py` 里，
就会出现 `models → app/__init__ → models` 的循环导入。
把 `db` 放进一个**不依赖任何业务模块**的文件，环就断了。

### Q5：什么时候建立数据库连接？
**第一次真正执行查询时**（懒加载），不是应用启动时。
所以 `run.py` 能正常启动、但一访问页面就报连不上库 —— 这是符合预期的行为，
不是 bug。

## 七、一句话速查

| 阶段 | 关键动作 |
|---|---|
| `run.py` 模块级 | 加 sys.path、导入 env_check |
| `main()` | argparse → `check()` 预检 → import app → `create_app()` → `app.run()` |
| `config.py` | 模块级就执行 `load_dotenv()`，把 .env 灌进 os.environ |
| `extensions.py` | 创建 `db` / `login_manager` 单例，**不绑定 app** |
| `create_app()` | Flask() → 配置 → init_app → **import models** → import 蓝图 → register ×9 → 注册过滤器/错误/CLI |
| `models` import | 定义了 10 个模型；`user_loader` 在这里**注册** |
| 请求进来 | 上下文 → 路由 → 装饰器链（login → editor）→ 视图 → Service → raw_query → MySQL |
| 响应返回 | Jinja2 渲染 → 返回 → 上下文弹出 → 连接归还池 |
