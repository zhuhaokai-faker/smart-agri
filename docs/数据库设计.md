## 0. 全局约定

### 字符集：为什么库、表两级都要显式写 utf8mb4

MySQL 5.7 的 `character_set_server` 默认是 `latin1`，忘了指定就中文乱码 ——
那是"不写就出错"的强制要求。

**MySQL 8.0 的服务端默认已经是 utf8mb4**，这一层的坑消失了。
但本项目仍然**库、表两级都显式写死**，理由变成了防御性的：
不依赖服务端配置，换一台服务器也不会出问题；同时让"这张表用什么字符集"
成为代码里可读的事实，而不是隐含假设。

⚠️ 但**客户端**字符集仍然受操作系统影响 —— 本机 `character_set_client` 实测仍是 `gbk`，
所以命令行执行 SQL 时依然要加 `--default-character-set=utf8mb4`。

```sql
CREATE DATABASE smart_agri
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_ai_ci;
```

**为什么用 `utf8mb4_0900_ai_ci`**：
这是 8.0 的默认 collation，基于 Unicode 9.0，
比 5.7 时代常用的 `utf8mb4_general_ci` / `utf8mb4_unicode_ci`
排序更准确、性能也更好。（那两个老 collation 在 8.0 里仍可用，只是为了兼容既有数据。）

**关键是全库统一 collation** —— 如果 JOIN 两侧 collation 不同，
MySQL 需要做隐式转换，会导致**索引失效**。

### 主键宽度：为什么统一用 `INT UNSIGNED` 而不是 BIGINT

本项目全部表的数据量在十万行以内，`INT UNSIGNED` 上限 42 亿完全够用。

**InnoDB 的二级索引叶子节点存的是主键值**，主键宽度直接决定
每个二级索引的大小。盲目用 BIGINT 会让每个二级索引每行多 4 字节，
索引整体膨胀、缓冲区命中率下降。

> "按数据量选主键宽度"比"统一无脑 BIGINT"更需要判断力。

### 时间类型

- 业务时间用 `DATETIME` 而不是 `TIMESTAMP`：
  `TIMESTAMP` 有 2038 上限，且写入时**随时区转换** ——
  审计日志要的是"记录的永恒真相"，不能随时区漂移。
- 审计日志用 `DATETIME(3)` 毫秒精度：写入频率高，同一秒可能几十条，
  秒级精度无法确定事件先后顺序。代价仅多 1 字节。
- `DATETIME` 而不是 `DATE` 的选择：注册时间、创建时间要精确到秒；
  而 `obs_date`、`harvest_date` 这类业务日期用 `DATE` 更贴合语义
  （"2024-03-15 收获"没有时刻含义）。

### 金额：为什么用 `DECIMAL` 不用 `FLOAT`

二进制浮点无法精确表示 0.1。跨年 `SUM` 十万行之后误差可见。

本项目按字段语义分配精度，而不是所有金额统一一个精度：

| 字段 | 类型 | 理由 |
|---|---|---|
| `price` / `unit_price` | `DECIMAL(10,4)` | 单价需要更高精度（如化肥 2.8375 元/kg） |
| `amount` / `output_value` | `DECIMAL(14,2)` | 金额到分即可（财务口径） |
| `yield_kg` | `DECIMAL(14,2)` | 产量精确到 0.01 kg |
| `quantity` | `DECIMAL(12,3)` | 用量常用千克/升，三位小数 |

## 2. 逐表设计论证

### 2.1 `user` — 账号 + RBAC

**关键决策 1：`password_hash` 用 `VARCHAR(255)` 而不是 `CHAR(60)`**

这条是实测踩出来的。常有人说"bcrypt 哈希固定 60 字符，所以用 `CHAR(60)`"。
这个说法在 werkzeug 3.x 上**直接导致写入失败**：

```
generate_password_hash('admin123')                → 162 字符（scrypt）
generate_password_hash(pw, 'pbkdf2:sha256')       → 103 字符
```

哈希的**算法和参数会随安全策略演进**（werkzeug 默认从 pbkdf2 换成 scrypt，
迭代次数也会周期性调高）。把列宽硬编码成某个算法的输出长度，
会在某次依赖升级后突然报 `Data too long for column`，
而且因为只在注册/改密时触发，很容易漏测。

**关键决策 2：`role` 用 `TINYINT` 不用 `ENUM`**

三个理由：
1. `ENUM` 的 `ORDER BY` / 比较按**内部索引序号**而非字面量，
   `WHERE role > 2` 的语义会随枚举定义顺序漂移，是隐形炸弹；
2. 加 `ENUM` 值虽可 INPLACE，但删除/重排枚举值必须重建表；
3. `TINYINT` + 应用层常量映射可索引、可 JOIN、可外键。

而 `ENUM` 唯一的"省空间"优势并不存在 —— `TINYINT` 也是 1 字节。

**索引**：
- `uk_username` —— 既是唯一约束，也是登录查询 `WHERE username = ?` 的索引
- `idx_role_status (role, status)` —— 服务"按角色筛选用户列表"

### 2.2 `farm` — 农场/合作社

**`longitude` / `latitude` 用 `DECIMAL(10,6)` 不用 `FLOAT`**

`DECIMAL(10,6)` 精度约 0.11 米，远超农业地块需求。
更重要的是 `DECIMAL` 是**精确值**，做地块距离计算和空间聚类时结果可复现；
`FLOAT` 是二进制浮点，同样的输入在不同聚合顺序下可能得到不同的尾数。

**`region_code` 放在 farm 而不是 plot**

气象是**按地区**的公共维度，多个农场/地块共享同一套气象数据。
放在农场级别能支持"同一气象区不同农场的产量对比"。

---

### 2.3 `plot` — 地块

**为什么有 `fertility_level`（肥力等级）字段**

它是**产量建模的分层依据**。造数时用它生成"优/中/差"三类基础单产
（差 35%），否则所有地块单产差不多，单产 TopN 排行和 ABC 分析都没有区分度。

**把"肥力等级"做成数据而不是硬编码，是领域建模的体现。**

**索引**：
- `uk_plot_no` —— 对外编号唯一
- `idx_farm_status (farm_id, status)` —— 服务"某农场下的在耕地块"。
  `farm_id` 等值在前、`status` 过滤在后，符合最左前缀原则。
  同时它的最左列 `farm_id` 充当外键索引。
- `idx_fertility` —— 服务按肥力分组统计

### 2.4 `crop` — 作物品种（本项目与普通 CRUD 项目的分水岭）

**`base_temp` 和 `gdd_maturity` 是本项目最重要的两个字段**

它们把**作物生理参数沉淀成数据**，而不是硬编码在 Python 里。
于是"有效积温是否达到成熟"这个判断可以**完全在 SQL 里完成**：

```sql
SELECT SUM(GREATEST(0, (w.temp_max + w.temp_min)/2 - c.base_temp)) AS gdd
...
HAVING gdd >= c.gdd_maturity
```

改作物品种不用改代码 —— 这是领域驱动设计的直接收益。

**为什么必须是字段而不是常量**

不同作物的差异很大：

| 作物 | 生物学零度 | 所需有效积温 |
|---|---|---|
| 小麦 | 0℃ | 1870 ℃·d |
| 玉米 | 10℃ | 1320 ℃·d |
| 黄瓜 | 12℃ | 620 ℃·d |
| 苹果 | 5℃ | 2990 ℃·d |

写成常量，多作物支持就无从谈起。

**这些值是怎么来的**

由 `scripts/calibrate_gdd.py` 按本项目的实际气候**标定**得出 ——
取该作物在适宜地区、真实播期窗口内，生育期长度上能积累的 GDD 中位数 × 0.95。

**这也是真实农艺的做法**：用多年平均积温确定品种熟期。

> 最初直接抄文献值（玉米 2400℃·d），实测发现各作物的
> "实际积温 / 所需积温"中位数只有 0.1~0.7 ——
> **所有作物在有生之年都积累不到成熟所需积温**。
> 后果是积温系数长期卡在保底区间剧烈波动，把施肥信号完全淹没。

### 2.5 `weather_daily` — 逐日气象

**为什么独立成表，不挂在 `planting` 上**

气象是**按地区、按日**的公共维度：同一气象站覆盖范围内的所有地块，
共享同一套气温降水数据。

若把 `temp_max` / `temp_min` 塞进 `planting` 或 `farming_log`：
- 每个地块每天都会存一份**完全相同的值** ——
  几十个地块 × 1095 天 = 数万行纯冗余；
- 更严重的是无法支持"**同一地区不同地块在同一气象条件下的产量对比**"，
  因为数据被复制成了互不相干的副本。

**`obs_month` 生成列**

```sql
obs_month DATE GENERATED ALWAYS AS
  (DATE_SUB(DATE(obs_date), INTERVAL DAYOFMONTH(obs_date) - 1 DAY)) STORED
```

`GROUP BY DATE_FORMAT(obs_date,'%Y-%m')` 用不上索引 ——
B+ 树里存的是 `obs_date` 原始值，不是格式化后的字符串。
用 `STORED` 生成列把月份首日物化并建索引，月度聚合就能走索引。

选 `STORED` 而非 `VIRTUAL` 是因为它要参与覆盖索引扫描。

**`uk_region_date (region_code, obs_date)` 一索引两用**：
- 唯一约束（同地区同日只能有一条）
- "某地区某时段气象数据"查询的索引

### 2.6 `planting` — 种植批次（枢纽表）

**`season_seq` 的线性性是刻意的**

```python
season_seq = 年份 × 2 + (春=1 / 秋=2)
```

相邻茬口恰好相差 1。**同期群分析**（留存）和**连续种植判定**都依赖这个性质。

- 用 `'2024春'` 字符串 → 相减无意义
- 只用年份 → 丢失同年春秋茬的区别
- 用 `202412` 年月编码 → 跨年时 `202412 → 202501` 差 **89 而不是 1**

**后者的 bug 只在跨年的连续段上暴露**，数据不足 12 个月永远发现不了。

**状态编号用 10/20/30/40 而非 1/2/3/4**

将来若要插入"部分收获 35"这类中间态，
`WHERE status BETWEEN 20 AND 40` 这类范围写法不会失效，
且 `status` 的大小顺序 = 农事推进顺序。

如果初始用 1,2,3,4，插入新状态时只能全表 UPDATE 重排 ——
**这是真实生产事故**。

**`uk_plot_crop_season (plot_id, crop_id, season)` 一索引三用**

1. 业务约束：同一地块、同一品种、同一茬口只能有一批种植记录
2. 该唯一键的最左前缀是 `plot_id`，**因此不需要再单独建 `idx_plot(plot_id)`**
3. 外键 `fk_planting_plot` 会复用它 —— 省下一个索引的写放大

> 如果当初把它定义成 `(crop_id, plot_id, season)`，
> MySQL 就会为了外键**额外自动创建一个单列 `plot_id` 索引** ——
> 这是隐形的写放大，也是"索引列顺序的影响远不止查询性能"的好例子。

**状态机**

```
10 待播种 ──▶ 20 生长中 ──▶ 30 成熟待收 ──▶ 40 已收获 (终态)
     └────────────▶ 50 已废弃 (终态)
                   └──────▶ 50 已废弃
```

合法流转：`10→20`、`10→50`、`20→30`、`20→50`、`30→40`
非法流转：`40→任意`、`50→任意`、`10→30`（跳过生长）

**为什么状态机要写在服务层**：

- 放模型里 → 模型会和 Flask 的 request/flash 耦合，变难复用
- 放视图里 → 换入口（API/脚本/定时任务）就要复制规则，迟早出现
  "网页上校验、脚本里不校验"的漏洞

**`CHECK` 约束在 8.0.16+ 真正生效**（5.7 只是解析后静默忽略），
所以现在数据库层也能兜底 —— 见下面「CHECK 约束」一节。

### 2.7 `farming_log` + `input_cost` — 为什么是两张表

它们回答的是**两个不同维度**的问题：

| 表 | 回答的问题 | 维度 |
|---|---|---|
| `farming_log` | 什么时间做了什么作业（含人工/机械费） | 过程 |
| `input_cost` | 买了什么、用了多少、多少钱 | 成本 |

合并成一张表会导致**大量 NULL**：
一次灌溉有工时但没有物资单价；买化肥有金额但没有作业描述。

**一张表两种语义、列大量为空，是典型的设计异味。**

**为什么 `labor_cost` 单独列而不只存工时**

工时本身不是钱。折算率（元/工时）随地区和年份变化，
存成金额才是**当期实际成本**。
用今天的折算率去重算三年前的工时是错的 —— 这是成本核算的基本要求。

### 2.8 `input_cost.amount` — STORED 生成列

```sql
amount DECIMAL(14,2) GENERATED ALWAYS AS
  (ROUND(quantity * unit_price, 2)) STORED
```

**为什么用生成列而不是普通列**

`quantity * unit_price` 是纯确定性、同行内计算。
交给数据库保证一致性，**应用层不可能写错、也不可能漏更新**。
用普通列就必须在每次 INSERT/UPDATE 时手工同步，
一旦有非应用写入（如运维直接改库）就会不一致。

**为什么选 `STORED` 而不是 `VIRTUAL`**

`VIRTUAL` 不占存储、读时计算，但每次读取都要重算表达式，
且**无法用于覆盖索引**（覆盖索引要求值真的存在索引里）。
`amount` 是高频 `SUM` 聚合字段，物化后可直接参与覆盖扫描。

代价是每次写入要计算并落盘 —— 对农资记录这种低频写入完全可接受。

### 2.9 `yield_record` — 分析层的核心事实表

**三个 STORED 生成列**

| 列 | 表达式 | 为什么 |
|---|---|---|
| `yield_per_mu` | `ROUND(yield_kg / NULLIF(harvest_area_mu, 0), 2)` | 最高频的分析指标 |
| `output_value` | `ROUND(yield_kg * unit_price, 2)` | 产值 |
| `harvest_month` | 收获月首日 | 让同比环比的月度聚合能走索引 |

**注意 `NULLIF(harvest_area_mu, 0)`**：生成列表达式里也必须防除零，
否则面积录入为 0 时写入会因 STRICT 模式报错。

**`plot_id` / `crop_id` 是刻意的分析型冗余**

它们可以从 `planting_id` 推导，但产量分析（按地块排行、按作物分组 TopN、
地图着色）几乎每次都要 JOIN `planting` 表，而 `planting` 本身还要
JOIN `crop` / `plot`。冗余后单表即可完成绝大多数分析，省掉两跳 JOIN。

**冗余是否安全，取决于被冗余的字段是否"事实上不可变"**。
`planting_id` 一旦确定，其 `plot_id` / `crop_id` 永不变更 ——
不存在"改了源表忘了改副本"的一致性风险。

**对比：`order_item` 型系统的快照冗余**

在订单系统里，明细表会冗余 `product_name` / `unit_price` 快照，
理由是"商品改名或调价后，历史订单必须能还原当时的成交价"。

但本项目 `yield_record.unit_price` **不是快照** ——
它是产量记录本身的属性（销售时的实际价格），不依赖任何外部表的可变字段。
**同样是冗余，语义完全不同，不能照搬。**

**索引设计**

| 索引 | 服务的查询 | 类型 |
|---|---|---|
| `uk_planting` | 一个批次只产出一条产量记录 + 充当外键索引 | 唯一 |
| `idx_crop_harvest (crop_id, harvest_date, yield_kg, yield_per_mu)` | 按作物统计产量（EXPLAIN 案例 1） | **覆盖索引** |
| `idx_plot_harvest (plot_id, harvest_date, yield_per_mu)` | 某地块的产量历史（EXPLAIN 案例 2） | 覆盖索引 |
| `idx_harvest_month_crop (harvest_month, crop_id, yield_kg)` | 同比环比的月度聚合 | 覆盖索引 |
| `idx_harvest_date` | 纯日期范围粗筛 | 普通 |

**`idx_plot_harvest` 的列顺序是刻意的**：
等值列 `plot_id` 在前、排序列 `harvest_date` 在后 ——
这是最左前缀原则最关键的一条推论：

```
索引 (A, B) 支持   WHERE A=? ORDER BY B     ✅
索引 (A, B) 不支持 WHERE B=? ORDER BY A     ❌
```

写反了会退化：`filtered` 从 100% 掉到 10%（见 `sql/03_optimize.sql` 的实测）。

### 2.10 `audit_log` — 操作审计

**`detail` 用 JSON，但 JSON 只当"不可查询的附件"**

不同表的变更字段完全不同（地块有面积、作物有积温）。
给它们建统一的列要么列数爆炸，要么大量 NULL。

**MySQL 8.0 有了 `JSON_TABLE`，可以把 JSON 展开成行了** ——
审计日志从"只能读不能查"变成了"可分析的数据资产"（见 `sql/06_audit_json.sql`）。

⚠️ 但**设计原则没有变**：`JSON_TABLE` 是运行时展开，**无法建立索引**。
所以需要**高频检索/排序**的字段仍然必须抽成独立列。
本项目用一个 STORED 生成列把"被修改的字段列表"抽出来：

```sql
changed_fields VARCHAR(255) GENERATED ALWAYS AS
  (JSON_UNQUOTE(JSON_EXTRACT(detail, '$.changed_fields'))) STORED
```

**JSON 列本身不能直接建索引，用生成列抽出来再建** ——
这是 5.7 时代处理 JSON 检索的标准姿势。
8.0 之后有了 `JSON_TABLE`，这条路不必再走了 ——
但**生成列的方案依然更快**（可索引 vs 运行时解析），所以两者并存：
生成列服务高频点查，`JSON_TABLE` 服务偶发的分析型查询。

**其他决策**
- `ip VARCHAR(45)` —— 45 字节兼容 IPv6
- `ON DELETE SET NULL` —— 删除用户不丢审计记录
- 业务上应禁止对该表 UPDATE / DELETE

### 2.11 `dws_yield_monthly` — 预聚合汇总表

**为什么要冗余出这张表**

同比环比查询要对月度汇总自连接三次，每次都要重新扫描 `yield_record` 做 GROUP BY。

物化成物理表后，自连接退化为**主键点查**：

| | 扫描方式 | rows |
|---|---|---|
| 用视图 `v_yield_monthly` | 派生表 ×2（各扫 259 行）+ 临时索引 `auto_key0` | 259 |
| 用汇总表 `dws_yield_monthly` | `cur` 全扫 25 行 + `yoy` **eq_ref 主键点查** | 25 / 1 |

生产环境明细表是百万级，而月份数永远是几十行。

**代价**：汇总表会过期，需要刷新（本项目由 `sql/03_optimize.sql` 幂等刷新）。
**这是"预聚合"的固有代价：用一致性维护成本换查询性能。**

**为什么还要保留视图**

- 汇总表快，但**数据会过期**
- 视图慢，但**永远实时**

生产上两者并存：实时看板查视图，固定报表查汇总表，汇总表由调度刷新。

> ⚠️ 本机 `event_scheduler = OFF`，不能用 MySQL EVENT 做定时刷新。
> 真实项目应交给外部调度（Airflow / crontab / 应用内定时任务）。

## 3. 外键设计

### 三种删除策略及其理由

| 策略 | 用在哪 | 理由 |
|---|---|---|
| `ON DELETE RESTRICT` | `plot→farm`、`planting→plot/crop`、`yield→plot/crop` | **保护分析数据完整性**。农场下有地块就不能删农场；地块有种植历史就不能删地块。允许级联删除会让"去年这块地的产量"凭空消失。 |
| `ON DELETE CASCADE` | `farming_log` / `input_cost` / `yield_record` → `planting` | 这些是种植批次的**从属数据**，脱离批次没有独立意义。不级联会留下悬挂行污染聚合结果。 |
| `ON DELETE SET NULL` | 所有 `→ user` | 删除用户不应删除其操作记录。审计日志要保留"曾经有人做过这件事"。 |

### 外键的索引复用

MySQL 创建外键时，如果**没有**以该列作为最左前缀的索引，会自动创建一个。

本项目刻意让各索引的最左列覆盖外键列，因此**不会产生冗余的自动索引**：

| 外键 | 复用的索引 |
|---|---|
| `fk_plot_farm(farm_id)` | `idx_farm_status` 的最左列 |
| `fk_planting_plot(plot_id)` | `uk_plot_crop_season` 的最左列 |
| `fk_planting_crop(crop_id)` | `idx_crop_status` 的最左列 |
| `fk_flog_planting(planting_id)` | `idx_planting_type` 的最左列 |
| `fk_yield_planting/plot/crop` | `uk_planting` / `idx_plot_harvest` / `idx_crop_harvest` |

验证方法：

```sql
SELECT * FROM information_schema.STATISTICS WHERE TABLE_SCHEMA='smart_agri';
```

当前共 **73 条**索引列条目，没有一个是"为了外键而建"的冗余索引。

### 外键类型必须完全一致

外键两侧的字段类型必须**完全一致**（含 `UNSIGNED`），
否则建表会直接报 `errno 3780`。这是 MySQL 外键最常见的建表失败原因。

## 4. 视图层

6 个视图，设计原则是**保持扁平**（最多一层聚合）：

| 视图 | 用途 |
|---|---|
| `v_planting_detail` | 种植批次 + 地块 + 农场 + 作物的全维度展开 |
| `v_yield_detail` | 产量记录 + 全维度（分析 ②③④⑤⑥ 的基础） |
| `v_planting_cost` | 单批次成本结构（物资 + 人工 + 机械） |
| `v_yield_monthly` | 月度产量汇总（分析 ② 的基础） |
| `v_plot_yield_summary` | 地块级产量汇总（分析 ④⑤⑥ 与地图的基础） |
| `v_crop_region_yield` | 作物 × 地区交叉汇总 |

### 两个关键点

**1. `v_planting_cost` 必须先各自聚合再 JOIN**

```sql
-- ❌ 错误：5 条农资 × 8 条农事 = 40 行笛卡尔积
--         SUM(amount) 会把每条农资金额重复算 8 遍
FROM planting p
LEFT JOIN input_cost  i ON i.planting_id = p.id
LEFT JOIN farming_log l ON l.planting_id = p.id

-- ✅ 正确：先在子查询里聚合到 planting 粒度
LEFT JOIN (SELECT planting_id, SUM(amount) FROM input_cost GROUP BY planting_id) ic
LEFT JOIN (SELECT planting_id, SUM(labor_cost) FROM farming_log GROUP BY planting_id) fl
```

**这个错误不报错**，结果看起来只是"数字偏大"。
项目里有一条断言专门守它。

**2. 单产必须用 `SUM(产量)/SUM(面积)`，不能用 `AVG(单产)`**

```
A 号地：100 亩，单产 500  → 总产 50000
B 号地：  1 亩，单产 900  → 总产   900
正确 = (50000+900)/(100+1) = 503.96
错误 = (500+900)/2         = 700      ← 差了 39%
```

**直接对"比率"取平均是辛普森悖论的典型表现。**
大面积地块应该被赋予更大权重。

### 视图的性能真相（8.0 并没有改变这一点）

- MySQL 会把视图展开成派生表，**视图本身不存储数据**，每次查询都重新执行
- **视图 ≠ 性能优化手段**，它只是"保存下来的查询"
- 带 `GROUP BY` 的视图**无法被 `derived_merge` 合并**，会被物化成临时表
- 嵌套多层视图会带来实打实的性能问题

**真正要提升性能，得用汇总表（物化）。**
本项目刻意保持视图扁平，就是为了避免这个陷阱。

## 5. 一个完整的索引决策示例

以 `yield_record` 为例，展示"每条索引都要能说出服务哪个查询"：

| 索引 | 服务的查询 | 为什么是这些列、这个顺序 |
|---|---|---|
| `uk_planting` | ① 一个批次只产出一条产量记录（业务规则）<br>② 外键 `fk_yield_planting` 的索引 | 唯一约束即业务规则；最左列 `planting_id` 同时满足外键需求，避免自动创建冗余索引 |
| `idx_crop_harvest (crop_id, harvest_date, yield_kg, yield_per_mu)` | 按作物统计产量/单产（EXPLAIN 案例 1） | 最左列匹配 `GROUP BY crop_id`，可走索引顺序分组，消除临时表；四个列全在索引中 → 覆盖索引，完全不回表 |
| `idx_plot_harvest (plot_id, harvest_date, yield_per_mu)` | 某地块的产量历史，按日期倒序（EXPLAIN 案例 2） | 等值列 `plot_id` 在前、排序列 `harvest_date` 在后 → `ref` 访问 + `Backward index scan`，消除 filesort |
| `idx_harvest_month_crop (harvest_month, crop_id, yield_kg)` | 月度产量聚合、同比环比 | `harvest_month` 是生成列，用它替代 `DATE_FORMAT(harvest_date)` 从而能走索引 |
| `idx_harvest_date` | 纯日期范围粗筛（不带作物/地块条件时） | 最左列就是范围条件列 |

**没有一条索引是"先建着，以后可能用得上"。**
说不清服务哪个查询的索引，就是纯粹的写放大。

## 6. 【8.0 新增】CHECK 约束真正生效

### 从"装饰品"到"闸门"

MySQL 5.7 对 `CHECK` 的处理是：**解析它、存下来、然后完全忽略**。
也就是说下面这样的代码在 5.7 里毫无作用，脏数据照样能写进去：

```sql
CHECK (yield_kg >= 0)          -- 5.7：装饰品
```

**8.0.16 起 `CHECK` 真正强制执行**，违反会直接拒绝写入：

```
ERROR 3819 (HY000): Check constraint 'ck_yield_nonneg' is violated.
```

于是本项目可以做到**纵深防御**：

```
第一层  前端 required / min 属性   ← 体验优化，不是安全边界
第二层  服务层显式校验              ← 能给出可读的业务错误提示
第三层  数据库 CHECK 约束           ← 最后一道闸门，绕过应用也拦得住
```

### 本项目新增的 9 条约束

| 约束 | 表 | 拦住什么 |
|---|---|---|
| `ck_icost_nonneg` | `input_cost` | 负的用量 / 单价 |
| `ck_yield_nonneg` | `yield_record` | 负的产量 / 面积 / 单价 |
| `ck_flog_nonneg` | `farming_log` | 负的工时 / 费用 |
| `ck_planting_area` | `planting` | 种植面积 ≤ 0 |
| `ck_planting_status` | `planting` | 状态取值不在 {10,20,30,40,50} |
| **`ck_planting_dates`** | `planting` | **生育期日期逆序** |
| `ck_weather_temp` | `weather_daily` | 最高温 < 最低温；温度超出物理可能范围 |
| `ck_weather_nonneg` | `weather_daily` | 负降水 / 湿度 > 100% |
| `ck_plot_area` | `plot` | 地块面积 ≤ 0 |

### 最有价值的一条：生育期日期单调性

```sql
CHECK ((emerge_date IS NULL OR emerge_date >= sow_date)
   AND (flower_date IS NULL OR flower_date >= emerge_date)
   AND (mature_date IS NULL OR mature_date >= flower_date)
   AND (harvest_date IS NULL OR harvest_date >= mature_date))
```

**日期逆序不会让任何查询报错**，只会让生育期分析算出负数
（"出苗用了 −5 天"）—— 属于"结果错了但不报错"，正是 CHECK 最该拦的一类问题。

### ⚠️ CHECK 的定位：拦"荒谬性"，不拦"业务规则"

这个区分很重要：

| 类型 | 例子 | 能否用 CHECK |
|---|---|---|
| **数据荒谬性** | 负产量、日期逆序、温度超物理范围 | ✅ 可以 |
| **业务规则** | "已收获的批次不能退回生长中" | ❌ 不行 |

业务规则需要知道"变更前是什么状态"，是**跨行/跨时间**的问题，
`CHECK` 只能看到当前行。所以状态机仍然必须留在服务层。

**把 CHECK 当业务规则引擎用，会写出一堆难以维护的约束。**

### 附带的好处：约束即文档

这 9 条约束同时也是**数据模型的自我描述** ——
打开 `SHOW CREATE TABLE` 就能看到"这块地的面积必须为正""生育期日期必须有序"。
比写在代码注释里更难被忽略。
