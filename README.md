## 一、这个项目是什么

一个面向**种植合作社 / 家庭农场**的业务管理系统，覆盖从播种计划、农事作业、
农资投入到产量收获的完整闭环，并在此之上构建**数据分析与决策支持**能力。

| 模块 | 内容 |
|---|---|
| **数据看板** | 6 张图表：产量趋势、作物占比、单产排行、地区分布、成本结构、ABC 帕累托 |
| **地块地图** | ECharts 地块多边形热力图，可按单产/产值/面积/收获次数切换着色 |
| **8 组深度分析** | 每页 = 实际执行的 SQL 源码 + 结果图表 + 原理解析 + 5.7 对比 |
| **字段级变更分析** | ★ 用 `JSON_TABLE` 把审计日志的 JSON 展开成行（8.0 独有） |
| **业务管理** | 地块、作物品种、农场档案、种植批次、产量记录（可编辑 / 删除）、农事作业、气象数据 |
| **权限控制** | 三级 RBAC：管理员 / 农艺师 / 只读。**编辑产量给农艺师，删除只给管理员** —— 可逆的放开，不可逆的收紧 |
| **用户注册** | 公开注册（注册即只读）+ 管理员提权 + 三层防刷 + 三层重名校验 |

### 为什么是农业方向

市场上"电商管理平台"一类的作品集项目极多，技术栈雷同、业务无差异。
农业方向有几个独特优势：

1. **有真实的领域指标可讲** —— 有效积温、投入产出比、干旱预警；
2. **技术难点和业务耦合** —— 比如"连续干旱日数"必须排除冬季封冻期，
   这是纯技术视角想不到的一层；
3. **差异化** —— 面试时能讲清"有效积温怎么算、为什么这么算"的人极少。

## 二、核心亮点

### 2.1 八组分析，全部用上 8.0 的能力

| # | 分析 | 用到的 8.0 特性 |
|---|---|---|
| ① | **有效积温 (GDD) 累计** | `SUM() OVER (ORDER BY ... ROWS BETWEEN ...)` |
| ② | **产量同比 / 环比** | 自连接（**刻意不用 LAG**，见 3.2） |
| ③ | **单产影响因子相关系数** | 手写公式 + `STDDEV_POP` 交叉验证 |
| ④ | **投入产出比 ROI** | `RANK() OVER (PARTITION BY ...)` |
| ⑤ | **分组 Top N** | `ROW_NUMBER() OVER (PARTITION BY ...)` |
| ⑥ | **ABC 帕累托** | `SUM() OVER` + **具名窗口 `WINDOW` 子句** |
| ⑦ | **同期群留存** | **CTE** 拆解三层嵌套逻辑 |
| ⑧ | **连续干旱预警** | **CTE** + `ROW_NUMBER()` 实现 gaps-and-islands |
| ⑨ | **字段级变更分析** | **`JSON_TABLE` + `JSON_KEYS`**（5.7 完全做不到） |

### 2.2 每条 SQL 都配了"正确性断言"

在多数练手项目里，SQL 只要"能跑出结果"就算完事。但数据分析里最危险的情况是
**结果错了却看起来正常**。所以本项目有 `sql/05_tests.sql` + `scripts/verify.py`，
共 **30 条断言**：

```
✅ 外键完整性 / 生成列一致性 / 状态机自洽
✅ 冗余列一致性（yield_record 的 plot_id/crop_id 必须与 planting 一致）
✅ 收获日单一来源（yield_record 收获日 == planting 收获日）
✅ 同期群自检（季序=0 的留存率必为 100%）
✅ ABC 完整性（各分类地块数之和 == 总数；累计占比末行 == 100%）
✅ 两种 TopN 实现交叉验证（ROW_NUMBER 版 == 相关子查询版）
✅ 成本无重复累加 / 同比数据充分性 / GDD 累计单调性
✅ 【8.0 新增】相关系数两条数学路径必须一致
✅ 【8.0 新增】窗口帧 ROWS/RANGE 差异检测
✅ 【8.0 新增】证明"自连接 与 LAG(x,12) 不等价"
✅ 服务层函数与独立算法交叉验证   ← 见第十节
```

运行 `python scripts/verify.py` 一条命令全部校验，退出码可直接接入 CI。

### 2.3 页面上展示的 SQL 就是实际执行的 SQL

8 个分析页每个都渲染 **SQL 源码（语法高亮）+ 结果图表 + 原理解析**。

关键实现：`analytics_service.py` 里有一个 SQL 注册表，

```python
SQL = {}

def q(name, sql, params=None):
    SQL[name] = sql          # 登记实际执行的 SQL 原文
    return raw_query(sql, params)
```

页面渲染 `SQL['gdd_curve']` —— **与真正执行的是同一个字符串对象，结构上不可能漂移**。

> 如果采用"在文档里再抄一份 SQL 用于展示"的做法，只要改了查询忘了改副本，
> 页面显示的就是错的，而这种错误**不会报错**，只会在演示现场被问穿。

### 2.4 用户注册：把唯一对公网开放的写入口做成"只能看看"

"加个注册表单"听起来是个 20 行的活。但真正要想清楚的是三件事：

**① 注册后给什么权限？**

如果默认给可编辑角色，前面做的整个 RBAC 就白费了 —— 任何人都能注册进来改数据。

本项目的策略：**注册即只读（`role=3`）**，想要写权限必须由管理员在「用户管理」页手动提权。
这样即使注册被批量刷号，攻击者拿到的也只是一堆**只能看**的账号。

**② 重名校验为什么做三层？**

| 层 | 作用 | 拦得住什么 |
|---|---|---|
| 前端 AJAX 即时提示 | 体验（早发现、少一次往返） | 手误 |
| 服务端格式 + 重名检查 | 业务规则 | 绕过前端的直接 POST |
| **数据库 `uk_username`** | **最终防线** | **并发竞态** |

前两层都是"先查再写"，两次查询之间有**时间窗**：
两个并发请求可以同时查到"用户名可用"，然后都去插入。
**只有数据库唯一约束能拦住这种情况。**

**③ 怎么防刷？三层限制 + 两个机器人陷阱**

| 手段 | 阈值 / 机制 |
|---|---|
| 每 IP 每小时 | 3 个 |
| 每 IP 每天 | 10 个 |
| 全站每天 | 200 个（防分布式刷） |
| **蜜罐字段** | 一个 CSS 隐藏的输入框，正常人看不见；脚本会把所有 input 都填上 |
| **最短填写时间** | 表单加载时写入时间戳，提交时算差值；秒交的基本是脚本 |

限流的实现**复用了 `audit_log`**（本来就记录了 `action='REGISTER'` 和 ip），
没有引入 Redis 或新表。代价是数据量大了这个 `COUNT` 会变慢 ——
真实高流量场景该用 Redis 计数器 + 过期时间，这个边界写在代码注释里了。

**④ 两条防止"把自己锁在门外"的保护**

权限系统最经典的事故是管理员一次误操作把自己降权或禁用，然后没人能改回来：

- **不能修改/禁用自己** —— 界面不显示按钮，服务端也会拒绝
- **不能降权/禁用「最后一个可用管理员」** —— 这条更隐蔽：
  有多个管理员时第 ① 条拦不住，可能把最后一个也降掉

**⑤ 一个必须说清楚的取舍：用户名枚举**

注册页的 AJAX 校验接口**天然是一个用户名枚举入口** ——
攻击者可以逐个查询哪些用户名已被注册。
而登录接口我是刻意做成"用户名和密码错误返回同一句提示"来防枚举的。

为什么注册这里允许暴露？因为**注册本身无法避免这个信息泄露** ——
用户必须知道名字是否可用才能完成注册。
这是业内普遍接受的取舍，但它确实降低了攻击者猜密码的成本
（至少知道了哪些用户名真实存在）。所以我也给这个 AJAX 接口加了限流
（每 IP 每分钟 30 次）。如果哪天要收紧：去掉实时校验，只在提交后提示"已被占用"。

**⑥ 造数脚本不再清空 `user` 表**

注册进来的用户是**真实数据**，不是造出来的演示数据。
原来的 `clear_all()` 会把 user 一起 TRUNCATE，导致：

- 用户下次登录发现账号没了，没有任何提示
- 管理员手动提过的权限全部丢失
- 审计日志里那些 `user_id` 变成悬挂引用

现在改成"**只补缺失的演示账号，不碰已有的**"。
不用 upsert 覆盖是有意的：那会把管理员刚提的权改回演示值，很意外。
想恢复演示账号到初始状态，手动删掉再跑一遍即可。

> 这个改动本身引发了一个更隐蔽的 bug，见第十节的 **Bug 9**。

## 三、5.7 → 8.0 迁移实录

项目最初按 **MySQL 5.7** 编写（5.7 没有窗口函数和 CTE），后来整体迁移到 **8.0.46**。

**迁移不是改个版本号，而是重新验证每一条结论。** 下面是四处需要判断的地方。

### 3.1 逐日累计：用户变量 → 窗口函数

```sql
-- 5.7：三行技巧 + 两个必须同时满足的约束
@gdd := IF(@pid = t.planting_id, @gdd + t.gdd_daily, t.gdd_daily) AS gdd_cum,
@pid := t.planting_id AS _pid_guard        -- 漏了这行，累计直接失效
... ORDER BY w.obs_date LIMIT 18446744073709551615   -- 不加，ORDER BY 被 derived_merge 吃掉

-- 8.0：一行
SUM(GREATEST(0, (w.temp_max + w.temp_min)/2 - c.base_temp))
    OVER (ORDER BY w.obs_date
          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS gdd_cum
```

⚠️ `ROWS BETWEEN ...` 必须显式写。默认帧是 `RANGE`，它把 `ORDER BY` 值**相同的行算作同一帧** ——
对累计求和来说，有并列值时两者结果完全不同。

### 3.2 同比环比：**不能**改成 `LAG()`（最重要的一处判断）

很多人迁移时会顺手写成：

```sql
LAG(total_yield_kg, 12) OVER (ORDER BY harvest_month) AS last_year   -- ❌ 错的
```

**`LAG(x, N)` 数的是「往前 N 行」，不是「往前 N 个月」。**
本项目的月度数据**有断档**（缺失 2023-02、2024-03，那两个月份没有作物收获），
一旦有断档，第 12 行就不再是"去年同月"。

实测对照（数据来自本项目真实数据）：

| 月份 | 行号 | `LAG(x,12)` | 自连接（正确） |
|---|---|---|---|
| 2023-06 | 12 | `NULL` | 1648.5（2022-06）|
| 2023-07 | 13 | 1648.5（2022-06）| **6337.0（2022-07）** ← 差了一个月 |
| 2023-08 | 14 | 6337.0（2022-07）| **3305.8（2022-08）** ← 持续错位 |

**29 个月里有 18 个月两种写法结果不同，而且不会报任何错。**

所以同比环比**保留自连接**（`DATE_SUB(month, INTERVAL 1 YEAR)` 按日期值匹配，与行号无关）。
这条结论被固化成了断言 —— `sql/05_tests.sql` 的断言 8 会检测两种写法是否有差异，
如果哪天数据变成连续无断档的，断言会失败，提醒我重新审视这个结论。

> **迁移版本最大的风险不是"新语法不会用"，而是"以为新语法可以无脑替换旧写法"。**

### 3.3 相关系数：MySQL 缺失的函数比想象的还多

我原本以为"8.0 至少能用 `REGR_SLOPE()` / `REGR_R2()` 替代"，**实测发现是错的**。

逐个调用验证的结果 —— 下面这些在 MySQL 8.0.46 里**全都不存在**：

```
CORR · COVAR_POP · COVAR_SAMP · REGR_SLOPE · REGR_R2 · REGR_INTERCEPT
MEDIAN · PERCENTILE_CONT
```

它们都是 Oracle / PostgreSQL 的函数。MySQL 有的是
`STDDEV_POP` / `STDDEV_SAMP` / `VAR_POP` / `VAR_SAMP`。

于是换了一条**真正可行**的交叉验证路径：

```
路径① 展开式： (n·Σxy − Σx·Σy) / √[(n·Σx²−(Σx)²)(n·Σy²−(Σy)²)]
路径② 定义式： 协方差 / (标准差 × 标准差)，用内置 STDDEV_POP
```

两条路径数学来源完全不同，结果必须吻合。**实测 12 个作物全部一致**（小数点后 4 位）。
这比"我觉得公式是对的"可靠得多。

### 3.4 实测确认的几个环境差异

| 项 | 5.7 | 8.0 | 影响 |
|---|---|---|---|
| `character_set_server` | `latin1` | **`utf8mb4`** | 中文乱码的坑消失了（但仍显式声明）|
| 默认 collation | `utf8mb4_general_ci` | **`utf8mb4_0900_ai_ci`** | 已迁移 |
| 默认认证插件 | `mysql_native_password` | **`caching_sha2_password`** | **PyMySQL 必须装 `cryptography`** |
| `CHECK` 约束 | 解析但**静默忽略** | **真正强制执行** | 本项目新增了 9 条 CHECK |
| `character_set_client` | `gbk` | `gbk`（未变） | 命令行仍需 `--default-character-set` |
| `group_concat_max_len` | `1024` | `1024`（未变） | 仍是静默截断陷阱 |
| `derived_merge` | `on` | `on`（未变） | 派生表 ORDER BY 仍可能被丢弃 |

**`cryptography` 是必需依赖，不是可选项**：8.0 的 `caching_sha2_password` 有两条认证路径，
只装 PyMySQL 时可能因为服务端缓存命中而"碰巧"连上，
但**MySQL 服务一重启、认证缓存清空就会直接失败**。这是"能跑但不健壮"的典型。

## 四、技术栈与选型理由

| 层 | 选型 | 为什么 |
|---|---|---|
| Web 框架 | Flask 3.1 + 应用工厂 `create_app()` | 可测试、可多实例、避免循环导入 |
| ORM | Flask-SQLAlchemy | `joinedload` 解决 N+1 是经典考点 |
| 驱动 | PyMySQL + **cryptography** | 8.0 的 caching_sha2_password 需要后者 |
| **分析查询** | **原生 SQL via `text()`** | 窗口函数 / CTE / JSON_TABLE，ORM 一个都表达不了 |
| 前端 | Jinja2 + Bootstrap 5 + ECharts 5 | **零构建**，不需要 Node.js |

### 为什么 ORM 和原生 SQL 混用

不是"没统一好"，而是刻意的技术选型：

- **ORM 适合**：CRUD、关联加载、事务管理；
- **原生 SQL 必须用于**：窗口函数、CTE、`JSON_TABLE`、
  以及所有需要引用**实际执行语句**的展示场景。

面试里能主动说清"什么时候该用 ORM、什么时候必须落到 SQL"，
比只会其中一种强得多。

### 为什么前端不用 Vue / React

一个 Flask 后端项目为了画几张图就引入 Node.js + npm + 构建流程，
**收益远小于复杂度**。而且所有静态资源都**下载到本地** `static/vendor/`：

> **面试演示常常在没有外网的环境进行。依赖 CDN 的页面会变成一堆没有样式的裸 HTML。**

## 五、快速开始

### 环境要求

- Python 3.10+
- **MySQL 8.0**（本项目使用了窗口函数、CTE、`JSON_TABLE`、`CHECK` 约束）

### 步骤

```bash
# 1) 创建虚拟环境
py -3.12 -m venv .venv

# ⚠️ 之后**所有**命令都要用 .venv 里的解释器，不要直接敲 python。
#    如果敲了 python run.py 而 PATH 上的 python 是别的环境，会报
#    ModuleNotFoundError —— 那是解释器选错了，不是代码问题。
#    项目自带环境预检，会直接把正确的命令打印给你。

# 2) 安装依赖（前端无需 npm）
.venv/Scripts/python.exe -m pip install -r requirements.txt
# 若这一步报 UnicodeDecodeError，说明 requirements.txt 被改成了带中文的 UTF-8 ——
# 该文件必须保持纯 ASCII，原因见第十节的 Bug 6。

# 3) 配置数据库连接
copy .env.example .env
#    编辑 .env，填入你的 MySQL 密码
```

```bash
# 4) 建库建表（会重建所有表，有数据保护）
.venv/Scripts/python.exe scripts/init_db.py --force

# 5) 造数（3 年数据 + 118 条审计日志）
.venv/Scripts/python.exe scripts/seed.py

# 6) 生成地块边界 GeoJSON（必须在 seed 之后，它要读地块坐标）
.venv/Scripts/python.exe scripts/gen_geojson.py

# 7) 跑正确性断言（30 条，必须全绿）
.venv/Scripts/python.exe scripts/verify.py

# 8) 启动
.venv/Scripts/python.exe run.py
```

访问 <http://127.0.0.1:5000> ，或双击 **`start.bat`** 一键完成以上全部步骤。

### 临时让别人访问（不租服务器）

双击 **`start_public.bat`**，它会用 Cloudflare 快速隧道（`cloudflared`）把本机的
5000 端口映射到一个公网 HTTPS 地址，形如
`https://随机单词-xxxx.trycloudflare.com`。**不需要注册账号，也不需要租服务器**。
把那个地址发给别人即可访问；关掉窗口隧道立刻断开。

```
start_public.bat
   ├─ 1/2  以 --prod 启动应用（debug 关闭）
   └─ 2/2  cloudflared tunnel --url http://127.0.0.1:5000
                → https://xxxx.trycloudflare.com
```

**⚠️ 公开之前必须先理解这三道闸门，它们都不是"形式上的检查"：**

| 闸门 | 拦住什么 |
|---|---|
| `--prod`（关掉 debug） | Flask 调试器允许访问者在浏览器里**执行任意 Python 代码**。开着 debug 暴露到公网，等于把机器交出去 —— Werkzeug 那个 PIN 是防手滑的，不是安全边界 |

```

┌──────────┐      ┌──────▼──────┐      ┌──────────┐

└────┬─────┘      └──────┬──────┘      └────┬─────┘
     │                   │                  │
┌────▼──────────┐  ┌─────▼──────────────────▼─────┐
│ weather_daily │  │        planting              │
│  逐日气象      │  │  种植批次 + 状态机 + 生育期    │
└───────────────┘  └───┬──────────┬───────────┬───┘
              ┌────────▼───┐ ┌────▼──────┐ ┌──▼───────────┐
              │farming_log │ │input_cost │ │ yield_record │
              │(人工/机械费)│ │(物资成本)  │ │ + 3 个生成列  │

  audit_log          操作审计（JSON 存变更快照 → JSON_TABLE 可查）
  dws_yield_monthly  月度汇总表（DWS 层，预聚合）
```

### 10 个可讲的设计决策

1. **金额用 `DECIMAL` 不用 `FLOAT`** —— 二进制浮点无法精确表示 0.1。
2. **状态用 `TINYINT` 不用 `ENUM`** —— `ENUM` 的 `ORDER BY` 按**内部索引序号**，
   `WHERE status > 2` 的语义会随枚举定义顺序漂移。
3. **状态编号留间隔（10/20/30/40）** —— 将来插入中间态时范围查询不失效。
4. **`crop` 表存 `base_temp` / `gdd_maturity`** —— 把作物生理参数沉淀成数据，
   使"积温够不够成熟"能完全在 SQL 里判断。
5. **3 个 `STORED` 生成列** —— `yield_per_mu` / `output_value` / `harvest_month`，
   任何写入路径都保证一致，且物化后才能进覆盖索引。
6. **`yield_record` 冗余 `plot_id` / `crop_id`** —— 分析型冗余。
   **冗余安全的前提是被冗余字段"事实上不可变"**。
7. **`weather_daily` 独立成表按气象区组织** —— 气象是公共维度，避免数万行冗余。
8. **`season_seq = 年×2 + 季次`，线性递增** —— 同期群分析依赖"相邻茬口差 1"。
   用 `202412` 这种编码跨年时差 89 而不是 1。
9. **每条索引都能说出服务哪个查询** —— 说不出的就是废物索引。
   且刻意让各索引最左列覆盖外键列，**避免 MySQL 自动创建冗余索引**。
10. **【8.0 新增】9 条 `CHECK` 约束** —— 见下。

### 【8.0 新增】CHECK 约束真正生效

5.7 对 `CHECK` 的做法是：**解析它、存下来、然后完全忽略**。脏数据照样能写进去。
8.0.16 起**真正强制执行**，违反直接拒绝：

```
ERROR 3819 (HY000): Check constraint 'ck_planting_dates' is violated.
```

于是本项目做到了**纵深防御**：

```
第一层  前端 required / min 属性   ← 体验优化，不是安全边界
第二层  服务层显式校验              ← 能给出可读的业务错误提示
第三层  数据库 CHECK 约束           ← 最后一道闸门，绕过应用也拦得住
```

新增的 9 条约束里，最有价值的是**生育期日期单调性**：

```sql
CHECK ((emerge_date IS NULL OR emerge_date >= sow_date)
   AND (flower_date IS NULL OR flower_date >= emerge_date)
   AND (harvest_date IS NULL OR harvest_date >= mature_date))
```

日期逆序不会让查询报错，只会让生育期分析算出负数 —— 属于"结果错了但不报错"，
正是 CHECK 最该拦的一类问题。

> ⚠️ 注意 CHECK 的定位：它拦的是**数据本身的荒谬性**，而不是业务规则。
> "已收获的批次不能退回生长中"这种跨行状态流转 CHECK 表达不了，
> 仍然必须靠服务层的状态机。

## 八、SQL 调优案例（EXPLAIN 实测）

`sql/03_optimize.sql` 用**索引提示**实现可复现的前后对比，可反复执行。
**所有数字都是在本机 MySQL 8.0 上实测的。**

### 案例 1：索引列顺序消除临时表

| | type | key | Extra |
|---|---|---|---|
| 无索引 | `ALL` | NULL | **Using temporary** |
| `idx_crop_harvest(crop_id, harvest_date, yield_kg, yield_per_mu)` | `index` | idx_crop_harvest | **Using index** |

**考点**：索引第一列匹配 `GROUP BY` 列时，可用索引顺序分组。

### 案例 2：最左前缀原则（含反例）

```sql
SELECT harvest_date, yield_kg FROM yield_record
WHERE plot_id = 25 ORDER BY harvest_date DESC LIMIT 20;
```

| 索引（FORCE INDEX） | type | key_len | rows | filtered |
|---|---|---|---|---|
| `(harvest_date, plot_id)` ❌ | index | 7 | 20 | **10%** |
| `(plot_id, harvest_date)` ✅ | **ref** | 4 | **4** | **100%** |

**考点**：索引 `(A, B)` 支持 `WHERE A=? ORDER BY B`，**不支持** `WHERE B=? ORDER BY A`。
反例那个索引并非"完全用不上"，而是**边走边过滤、扔掉 90% 的行**。

> ⚠️ 实测踩到的坑：`USE INDEX` 是**提示**，8.0 的优化器可以直接忽略它
> （于是演示不出反例索引有多差）；`FORCE INDEX` 才是**强制**。
> 做对照实验必须用后者。

### 案例 3：函数导致索引失效

```sql
GROUP BY DATE_FORMAT(harvest_date, '%Y-%m')   -- ❌ type=ALL（优化器直接放弃索引）
GROUP BY harvest_month                         -- ✅ 用 STORED 生成列
```

### 补充：`skip_scan` —— 8.0 的新优化

8.0 新增的 `skip_scan`（默认开启）**部分打破了最左前缀原则**：
它可以跳过联合索引的最左列，但**前提是最左列基数要低**。

实测（查询 `WHERE plot_id = 25`，只提供 `(crop_id, plot_id)` 这一个索引）：

| | type | rows | Extra |
|---|---|---|---|
| `skip_scan=ON` | **range** | **53** | **Using index for skip scan** |
| `skip_scan=OFF` | index | 259 | Using index |

扫描行数 **259 → 53**（少 4.9 倍）。原因：`crop_id` 只有 **12 个不同值**。

而换成 `(harvest_date, plot_id)`（212 个不同值）时**完全不触发** ——
要跳 212 次还不如直接扫一遍。

> **skip scan 不能替代正确的索引设计**：
> 该建的 `(plot_id, harvest_date)` 还是要建。
> 它是"没有正确索引时的补救"，不是"正确索引的替代品"。

## 九、演示数据说明

| 表 | 行数 |
|---|---|
| 农场 / 地块 / 作物 | 5 / 60 / 12 |
| 种植批次 | 327（5 种状态齐全）|
| 农事记录 / 农资投入 | 3125 / 2507 |
| 逐日气象 | 5480（5 个气象区 × 1096 天）|
| 产量记录 | 259 |
| **审计日志** | **118（含 before/after 变更快照）** |

### 为什么必须造满 3 年

**同比需要跨 13 个月以上取样。** 只造 12 个月的话，"去年同期"永远落在数据范围之外，
同比列全是 `NULL` —— 功能看起来"能跑"但完全没有结果。

### 植入的 7 类分布

如果所有数值都是均匀随机数，所有曲线都会变成直线。所以刻意植入了：
季节性、同比增长 10%/年、地块质量分层、施肥响应曲线（边际报酬递减）、
气象影响、地区差异、状态机自洽。固定 `random.seed(42)` 保证可复现。

### 两个关键取舍

**① 相关系数为什么是 0.4~0.6 而不是 0.9**

- **算出来 r ≈ 0.9 反而假** —— 影响单产的因素很多，施肥只是其中之一；
- **r 太低（<0.3）也不行** —— 散点图会变成一团噪声；
- **方差预算是共享的** —— 把 r 硬推到 0.8 只能压低地力差异和气象影响，
  那分析 ①④⑤⑥ 就全变成直线了；
- 还有个真实的统计学原因：**皮尔逊只度量线性关联**，
  而施肥的真实关系是对数型（边际报酬递减，曲线是凹的），r 本身就被系统性低估。

**② 积温参数是标定出来的，不是抄的**

最初照文献填玉米 2400℃·d，实测发现所有作物的"实际/所需积温"中位数只有 0.1~0.7 ——
**所有作物在有生之年都积累不到成熟所需积温**。改用脚本按本地气候标定
（这也是真实农艺做法），现在玉米 1320、小麦 1870、白菜 950，都落在真实区间。

## 十、项目中的真实 Bug 记录

这部分刻意保留 —— 它比"项目一次写对"更有价值。

### Bug 1：用户变量的"记住上一行"赋值被漏掉（最严重，5.7 时代）

```sql
-- ✅ 正确
@gdd := IF(@pid = t.planting_id, @gdd + t.gdd_daily, t.gdd_daily) AS gdd_cum,
@pid := t.planting_id AS _pid_guard        -- ← 这行漏了
```

**后果**：`@pid` 恒为 `NULL` → IF 永远走 else 分支 → "累计值"退化成"当日值"。
实测 GDD 曲线末行显示 **13.15**，真实值 **1138.61**。
同样的错误还出现在干旱预警里，导致查询返回 **0 行**。

**这类 bug 最危险的地方**：不报错、不崩溃，只是静默返回错误结果。

**发现方式**：原有 SQL 断言用的是它自己内联的 SQL，管不到服务层。
**防复发**：在 `verify.py` 里加了一组**服务层断言**，直接调用服务层函数交叉验证。

> 迁移到 8.0 后，这类错误**在结构上变得不可能发生** ——
> `SUM() OVER (PARTITION BY ...)` 和 `ROW_NUMBER() OVER (PARTITION BY ...)`
> 自带分区语义，不存在"忘记记住上一行分组"这回事。
> **这是窗口函数最大的价值：不是代码变短，而是错误变得不可表达。**

### Bug 2：领域知识缺失 —— 冬季封冻被误判成旱情

干旱预警最初没有温度条件，结果黑龙江查出来的"最长干旱"是
**1~2 月的 53 天，期间均温 −14.9℃**。

**那不是旱情，是冬季封冻** —— 东北的冬天本来就几乎不降水，作物也不生长。
加上 `AND temp_avg >= 5` 后，查出来的全部是春夏生长季的干旱过程。

> **农业干旱的定义前提是"作物处于生长状态且水分亏缺"** ——
> 这是纯技术视角想不到的一层，必须靠领域知识补上。

### Bug 3：成本模型没按面积缩放

人工费最初写成 `uniform(0.5, 4.0)` 工时（**与面积无关**），
结果 300 亩的地块只算了 2 小时人工，亩均成本只有 250 元 ——
而真实农业成本是粮食约 800 元/亩、设施蔬菜 5000~8000 元/亩。

成本低估 20 倍，导致投入产出比算出 **103 倍、利润率 10250%** 这种荒谬结果。

**危险之处**：**查询本身完全正确**，错的是输入数据。
"结果看起来不合理"往往要先怀疑数据口径而不是 SQL。

### Bug 4：测试写错，浪费时间去查不存在的问题

有一条断言写成"所有批次的收获日期不得晚于数据截止日"，报出 19 条"越界"。
但那些是 2024 年秋播的冬小麦/油菜，收获期在 2025 年 3~6 月，状态是"生长中" ——
**它们有未来的预计收获日期是完全正确的**。

> **是断言写错了，不是数据错了。测试本身也要被审视。**

### Bug 5：迁移中我自己犯的错 —— 漏写 `SET` 导致对照实验失效

写 `sql/03_optimize.sql` 的 `skip_scan` 对照时，我写了两组 EXPLAIN，
但**忘了在其中一组前面加 `SET SESSION optimizer_switch='skip_scan=off'`**，
结果两组跑的是同一个设置，输出一模一样。

> 这类错误在"写文档"时特别常见：**看起来做了对照，实际上没有**。
> 后来我把 `SET` 语句和一段自嘲的注释一起留在了文件里。

### Bug 6：`requirements.txt` 带中文，在中文 Windows 上 pip 直接崩

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xa4 in position 99
decoding with 'cp936' codec failed
```

**根因**：pip 读取 `requirements.txt` 时用的是**系统 locale 编码**，
只有在检测到 **UTF-8 BOM** 时才按 UTF-8 解码。
中文 Windows 的 locale 是 GBK/cp936，而文件是 UTF-8 无 BOM —— 于是中文注释
直接把 pip 打挂。

**为什么一直没发现**：我此前装依赖都是用显式包名
（`pip install Flask==3.1.3 ...`），**从来没走过 `-r requirements.txt` 这条路**。
而 README 的「快速开始」第一步恰恰就是这条命令 ——
等于新用户拿到项目第一步就卡死。

**修复**：`requirements.txt` 按惯例保持**纯 ASCII**，中文说明全部移到
README 和 docs/。文件顶部写明了"不要在这里加中文注释"及原因。

**顺带排查**：项目里其他会被外部工具读取的文件也过了一遍 ——
`.env.example` 纯 ASCII；`.gitignore` 由 git 读取（git 处理 UTF-8 没问题）；
SQL 文件由我们自己的代码以 `encoding='utf-8'` 显式读取，安全。

### Bug 7：`start.bat` 用了 LF 换行，双击直接失效

```
'杂分析平台' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'此时不应有 from ...'
```

**根因**：**Windows 批处理文件必须用 CRLF 换行。**
用 LF 时 `cmd.exe` 的解析器会错乱，具体表现为两类错误：

- `echo` 的中文被从中间劈开，后半截被当成命令名；
- 多行 `if (...)` 块被误解析，报「此时不应有 ...」。

**实测对照**（同一份内容，只改换行符）：

| 换行 | 结果 |
|---|---|
| LF | ❌ 退出码 255，满屏解析错误 |
| **CRLF** | ✅ 中文正常、`if not exist (...)` 块正确执行 |

**为什么没发现**：我用 Bash heredoc 生成的文件，天然是 LF。
而我在 Git Bash 里测试时又踩了另一个坑 —— `cmd.exe /c` 会被 MSYS 做路径转换
（`/c` 变成 `C:\`），导致 cmd 收到的是交互模式而非 `/c` 开关。
一度让我以为是"路径里的中文"的问题。**排除掉调用方式的干扰后才定位到换行符。**

**修复**：
1. `start.bat` 转为 CRLF；
2. 新增 **`.gitattributes`** 强制 `*.bat text eol=crlf` ——
   否则 `core.autocrlf` 配置不同、或项目在 Linux 上 clone 过再传回 Windows，
   换行符会被重新转成 LF，`start.bat` 又静默失效。

### Bug 8：包装对了，却依然 `ModuleNotFoundError`

```
ModuleNotFoundError: No module named 'flask_login'
  File ".../app/extensions.py", line 15, in <module>
      from flask_login import LoginManager
```

**这个 bug 的特点是：报错位置和真实原因完全不在一处。**

`flask_login` 明明已经装好了（在项目的 `.venv` 里），
但 **PATH 上的 `python` 指向的是另一个环境** ——
本机上是 `C:/Users/pycharm/PycharmProjects/PythonProject1/.venv`，
一个和本项目毫无关系的 venv。

实测确认：`flask_login` **只存在于**项目 `.venv`，
另外三个候选环境（PyCharm venv / 系统 Python / WindowsApps python）全都没有。

**为什么难排查**：堆栈指向 `app/extensions.py:15`，
看代码会以为是自己写错了 import。实际代码没问题，是解释器选错了。

**修复**：光"记住要用对解释器"是没用的 —— 迟早会忘。所以做了两件事：

1. **`env_check.py` 环境预检**，接在**四个入口**（`run.py` + 三个脚本）上。
   它检查"是否在虚拟环境里""是不是本项目的 .venv""关键依赖能否导入"，
   任何一条不过就打印**可操作的提示**（正确的解释器路径 + 具体命令）后退出，
   而不是抛出指向无关文件的 `ModuleNotFoundError`。

   ⚠️ 预检必须放在**所有第三方 import 之前** ——
   否则依赖缺失时会先炸在 `import pymysql` 那一行，预检根本轮不到执行。
   这是第一版写错了、复测时才发现的。

2. **`.vscode/settings.json`** 把解释器指向项目 `.venv`，
   VS Code 打开项目就自动选中，不用手动切。

**顺带修的一个逻辑瑕疵**：预检最初无论什么情况都提示"依赖缺失，补装即可"。
但**环境选错时，依赖"缺失"只是症状不是原因** ——
让人去 pip install 会把依赖装到别的项目上，本项目依然跑不起来。
现在会明确区分两种情况，并提示"**不要**在错误的环境里 pip install"。

> 这类"报错位置误导"的问题最消耗时间。
> 花 20 行代码在入口处拦下来，比每次都去翻堆栈划算得多。

### Bug 9：造数结果会随"用户表里有多少人"而变化（最隐蔽的一个）

**现象**：把 `user` 表从"不参与造数"改成"保留注册用户"之后，
造数跑出来的相关系数变了 —— 玉米从 0.524 变成 0.156，辣椒从 0.562 变成 0.032。

样本数没变、代码没动公式，只是**没再 TRUNCATE user 表**。

**根因**：`random.choice(seq)` 内部用 `_randbelow(len(seq))` 实现，
而 `_randbelow` 是**拒绝采样** —— 消耗多少个底层随机位，取决于列表长度和抽到的值。

于是 `rng.choice(用户列表)` 的消耗量会随**用户表里有多少个账号**变化。
一旦有人注册，user 表变长，后续**所有业务数据的随机序列整体偏移**。

这直接破坏了项目最核心的性质之一：**固定种子必然可复现**。
而可复现性对演示是刚需 —— 重跑一次数据和之前的截图对不上就废了。

**排查中的弯路（值得记下来）**：
我第一次验证时写了个小实验，对 n=2/4/9 各做 5 次 `choice` 再看后续随机数，
结果三者完全相同，于是**错误地排除了这个可能**。
后来又试了别的方向，绕了一圈才回来。

真正的问题是我那次实验**样本太小** —— 拒绝采样是概率性的，
5 次碰巧没触发重抽。改成 200 次之后立刻暴露：

```
200 次 choice(范围= 2) 之后，下一个 random() = 0.0505883295
200 次 choice(范围= 4) 之后，下一个 random() = 0.0505883295
200 次 choice(范围= 9) 之后，下一个 random() = 0.1904099144   ← 变了
200 次 choice(范围=20) 之后，下一个 random() = 0.0709930860   ← 也变了
```

**教训**：用随机性做实验时，"跑几次看起来一样"不能作为证据。
要么把样本量提到足以暴露概率性行为，要么直接去读实现。

**修复**：给"选操作人"配一个**独立的随机源**（`make_user_picker`），
让它完全不碰主 rng。这样无论 user 表怎么变，业务数据的随机序列都不受影响。

**验证**：用户数 9 → 12 → 9，三次造数结果**完全一致**。

### Bug 10：断言套件变红，但三条失败全是"正常使用"造成的

**现象**：准备发第一版时跑 `verify.py`，**27 通过 / 3 失败**。
而这三条失败**不是脏数据** —— 是在页面上正常操作（把批次从"生长中"一路
推进到"已收获"、录入几条产量）之后出现的。

**逐条查根因，发现两错一对**：

| 失败的断言 | 性质 |
|---|---|
| `status=40 必有产量记录` | **断言写错了**：`planting_service.suggest_next_actions()` 本来就会对这类批次提示"已标记收获，但尚未录入产量记录"，录入页的待办查询也是按这个条件筛的 —— 项目一直把它当**合法待办**，只有断言说它不合法 |
| `已收获批次的收获日不越界` | **断言写错了**：判据写死成 `> '2024-12-31'`（种子数据的截止日）。一旦有人把 2025 年茬口的批次推进到"已收获"就立刻变红 —— **把"数据集的窗口"当成了"业务的规则"** |
| `yield_record 收获日 = planting 收获日` | **真 bug**，见下 |

**真 bug 的根因**：录入产量的表单里有一个可填的「收获日期」，
而表单值会覆盖批次上的收获日（`_parse_date(表单) or p.harvest_date`）。
于是同一次收获有了两个日期，而且**不一致不会报错** ——
实测写出一条 `harvest_date=2025-08-30` 而批次是 `2025-08-23` 的记录，
是断言把它抓出来的。

**修复**：
1. 收获日改为**以批次为唯一来源**，表单里那个输入框换成只读展示
   （不是删掉 —— 用户仍然需要看到它，只是不能再改）；
2. 把两条写错的断言改成真不变式：`'2024-12-31'` → `CURDATE()`；
   "40 必有产量记录"换成"冗余列 `plot_id/crop_id` 与 planting 一致"
   （这条正好守住新加的编辑功能 —— 编辑路由刻意不暴露这两列）；
3. "已收获但未录产量"降级为**信息性上报**（只报数量、不出 PASS/FAIL），
   让它可见但不再判定失败 —— 否则"删除一条产量记录"这个正常操作
   会把测试弄红。

**教训（比 bug 本身更值钱）**：
- **断言会腐烂。** 它是照当时那份数据集写的，数据集一变就可能失真。
  判据要相对"永恒的规则"（收获日不能在未来），不能相对"造数那天的日期"。
- **测试写错比代码写错更危险**：Bug 4 已经踩过一次（报出 19 条不存在的
  "越界"），这次是同一个坑换了个地方。测试变红时第一反应应该是
  "是数据错了还是测试错了"，而不是直接去改数据。
- **断言套件本身也会和产品决策冲突**：加了删除功能之后，
  "40 必有产量记录"就从真不变式变成了假不变式。改产品时得回头看看
  哪些断言的前提被推翻了。

### Bug 11：`start_public.bat` 里的中文让 cmd 从行中间开始执行

**现象**：新写的公网启动脚本里带着中文注释和中文提示，运行时冒出这种错：

```
'模式、实际隧道指向别处"是这里最容易出的错，必须挡住。' 不是内部或外部命令
'例，等于把调试器暴露出去。' 不是内部或外部命令
```

注意报错的内容都是**某一行的后半截** —— cmd 把中文行从中间劈开当成命令执行了。

**根因**：cmd 解析批处理文件时是**按字节偏移**推进读指针的。
文件里有 UTF-8 多字节字符时，这个偏移会漂移，于是解析器"迷路"到行中间。
`chcp 65001` 并不能修好它。

**排查过程（和 Bug 9 一样的教训，只是方向相反）**：
我做了三变体对照 —— UTF-8 无 BOM / UTF-8 带 BOM / GBK：

| 变体 | 第一次跑 | 第二次跑 |
|---|---|---|
| UTF-8 无 BOM + `chcp 65001` | 坏（报错如上） | 坏 |
| **UTF-8 带 BOM** + `chcp 65001` | **正常** | **坏了**（`'@echo' 不是内部或外部命令`） |
| GBK | 本终端下乱码 | — |

带 BOM 那一栏是关键：**我第一次跑通就下了"BOM 是解药"的结论，复跑直接被打脸**。
两个文件的头 24 个字节逐字节比对完全相同，差别只在"什么时候坏" —— 说明这是个
**概率性**的解析问题，单次运行的结果不能作为证据。

> Bug 9 的教训是"跑几次看起来一样，不能证明没问题"；
> 这次是它的镜像："跑一次成功，不能证明修好了"。
> 概率性 bug 的验证必须**重复足够多次**，或者干脆绕开它。

**修复**：`start_public.bat` 改成**纯 ASCII**（提示语全部英文），
中文说明移到本 README。构建时用 `encode('ascii')` 而不是 `utf-8` ——
这样万一以后有人加了中文，会**直接报错**而不是安静地写出一个偶尔会坏的脚本。

这跟 Bug 6（`requirements.txt` 必须纯 ASCII）是同一个结论：
**会被外部工具拿去解析的文件，就把非 ASCII 字符留出去。**

**顺带**：
- `start.bat` 里也有中文，目前一直能跑 —— 但按上面的结论，它属于同一类风险，
  只是还没被触发。这条留在这里备查。
- 等待应用就绪原本写的是 `timeout /t 6`，但在 PATH 上存在 GNU coreutils 的环境里
  会解析成 Unix 的 `timeout` 并报 `invalid time interval '/t'`。
  改成 `ping -n 7 127.0.0.1 > nul` —— 这个写法不依赖 PATH 上有哪个 `timeout`。

## 十一、已知限制

诚实列出限制，比假装完美更可信：

1. **`成熟待收` 状态只有 1 条数据** —— 这是**正确的**：数据截止 2024-12-31，
   冬季没有作物处于"成熟了但还没收"的状态。
2. **小样本作物的相关系数不稳定** —— 每个作物只有 6~50 条记录，r 的抽样波动可达 ±0.3。
   用"分作物 + 跨作物汇总（相对单产归一化）"两个口径并列缓解。
3. **地图的地块边界是合成的** —— 地块边界在业务上属于"农场自己的数据"。
   要换成真实 shp 用 `scripts/from_shp.py`。
4. **`JSON_TABLE` 无法建索引** —— 它是运行时展开，每次查询都要解析 JSON。
   需要高频过滤的字段仍应抽成独立列。
5. **分页统一用 `LIMIT/OFFSET`** —— 数据量大时应改游标分页。
6. **未做 API 限流**；无单元测试框架（当前用 `verify.py` 的断言代替）。
7. **公网演示期间公开注册是开着的** —— `ALLOW_REGISTRATION` 默认 `true`，
   隧道开着时任何人都能注册一个只读账号。演示完应立即关掉隧道窗口。
   要长期开放的话，把 `.env` 里的 `ALLOW_REGISTRATION` 改成 `false`
   （这个开关做成配置项而不是写死，就是为了这种时候不用改代码）。
8. **Flask 内置服务器只适合演示** —— 隧道跑的就是它。它能扛住几个人的演示，
   但不具备多进程、超时控制、优雅重启。真要长期对外，换 waitress（Windows）
   或 gunicorn（Linux）即可，`create_app()` 工厂不用改。
7. **删除产量记录后，批次仍是"已收获"** —— 状态机里 `40` 是终态，没有回退路径，
   所以删除不会把批次退回"成熟待收"。批次会重新出现在「录入产量」的待办列表里，
   可以补录（唯一约束 `uk_planting` 随记录一起释放）。
   这在项目里是**设计好的待办状态**，不是残留的不一致 ——
   `planting_service.suggest_next_actions()` 本来就会对这类批次提示
   "已标记收获，但尚未录入产量记录"。
   删除前的完整快照写进 `audit_log`，记录本身则不可恢复；这也是删除只给管理员的原因。
